# Changelog

## Unreleased

- **New (experimental)**: prompts, "ask the reader at a step". `usePrompts` (from `./experimental`) records an answer per prompt, judges it (`prompt.judge`, else `judge`, else equality with `prompt.answer`, else unjudged; sync or async, a late verdict after a restart, input change or another prompt is dropped), scores it (`run.score`) and stops forward moves at an unanswered question. Prompts come from a generator step's `prompt` (the answer is the value of that `yield`, so a story branches on it) or from an `ask` overlay over any trace (predict mode). Settings: `retries` (default 0: the first answer settles a prompt), `navigation` `"gate"` / `"free"`, `autoContinue`, `enabled` / `defaultEnabled` / `readerToggle`, `onInputChange` `"lock"` / `"clear"` / `"keep"` (default: lock once a judged prompt is reached, else keep; `run.inputLocked`, `run.requestInput`, `restart()`), and `syncAnswers` (answers in the URL, restored with `syncInput` before the frame). `usePromptHistory` keeps the futures an answer cut off (`branches`, `backtracks`, `restore`). The answer record, `isChoicePoint`, `createWalkSession` and the branch tree (`addPath`, `branchesOf`) are pure and exported from `./core`.
- **Changed (experimental)**: `prompt` on a step is meaningful. An object `prompt` makes a question / choice point (like `await: true`); a string, `null` or an array under that name stays plain step data.
- **New**: `stopAt(frame)` on `useStepPlayer`, `useTrace`, `useSimulation` and `useWalk` (optional, additive): forward moves (next, a seek or scrub ahead, a link jump, playback) stop on the first frame it returns true for. A `useWalk` caller that passes `stopAt` also gets a gated link jump.
- **Changed (experimental)**: the walk step cap (`maxSteps`) counts steps since the last prompt, not the whole run, and a forward run continues the live generator instead of replaying it (`createWalkSession`).
- **Changed (experimental)**: answer links (`syncAnswers`, the kit's `${id}.a`) are off by default for judged runs (opt in with `prompts.linkAnswers`), since a link would carry the answers. A link carries each answer's final value only (restored entries regain their retries), and a list holding a single skipped entry round-trips as empty.
- **Changed (experimental)**: `ask` is called even while prompts are disabled (answers stay recorded, links never depend on `enabled`), and a `hashchange` that carries a new input while the input is locked is applied as navigation.
- **Changed (experimental)**: the kit's predict mode runs on `usePrompts`. It settles on the first answer by default (retries 0): a miss reveals the answer and waits for Continue, with no Skip under the default gate. Stepping with Next stops at an unanswered question (before, only autoplay held). `PredictApi.held` now means "the playhead is on a prompt", and Check with nothing picked no longer uses an attempt. The `hint` shows after a miss while a retry remains (set `prompts.retries`).
- **New (experimental)**: kit: `prompts` on a definition (`ask`, `judge`, `retries`, `navigation`, `autoContinue`, `onInputChange`, `linkAnswers`), the `Prompt` part, `promptsEnabled` on an explainer (an exam: overlay prompts forced on or off, no reader toggle) and `useExplainer().prompts`. `Predict`, `PredictToggle`, `Choices` and the `predict` block remain as shortcuts for this release (`Predict` is `Prompt`; `Choices` is `Prompt` on a run with prompts). A walk explainer keeps `retries: Infinity` and `onInputChange: "keep"`.
- **Changed (experimental)**: the kit's `predict` block defaults to `onInputChange: "clear"` (an input edit clears the answers; a definition's own `prompts.onInputChange` still wins), so a predict explainer's input stays editable after an answer. Under a lock, `Prompt` shows a Start over button (`restart()`), on a prompt or off it. A free-text prompt (no options) without `render` draws no options and warns once in development. `usePrompts` releases a hold whose prompt is gone (prompts turned off, an input change moved it) unless the page's own `holdAt` keeps the frame. A walk explainer's `.path` link accepts a step's own prompt options and otherwise checks `choose` (its parse, or its option list).
- **Fix (experimental)**: `precompute` of a simulation with step prompts stops at the first prompt (with `choices: []`), as the client's run does before any answer; it used to run past every prompt, so the scrubber and the no-JS HTML showed the future.
- **Demo**: `/adventure`, a text adventure that branches on picked and typed answers, with Back, and the paths a changed answer cut off kept in history. `/simulate`'s predict mode is `usePrompts` with a score and `onInputChange: "clear"`. The guide's predict and walks sections are one, "Ask the reader".
- **Docs**: LLMS.md section 10 (prompts), the API reference's "Experimental: prompts" group, and the kit entries updated for the shortcuts.
- **Fix**: `ChapterNav` keeps the active chapter in view. When the chapters don't fit, the row scrolls sideways, and the active one used to scroll off the end as the reader moved down the page. The row itself scrolls (the page doesn't).
- **Docs**: a guide for people at [/guide](https://stepwise.thesphynx.net/guide): one goal per section, from a first player to the authoring kit, each with a live example whose code is its real source, plus common mistakes (symptom, cause, fix) and the vocabulary.

## 0.6.0 — unreleased

The authoring kit: an explainer from a definition, a view and one tag, from
TSX or MDX. Three new entry points, all experimental (they may change in a
minor release). Additive: the root entry and `./experimental` keep every
export.

- **New (experimental)**: `@sphynxoid/stepwise/core`, the pure half of the library (simulations, traces, walks, re-anchoring, alignment, verdicts, explainer definitions and the schema) with no `"use client"` and no React at runtime, for server components, route handlers and build scripts.
- **New (experimental)**: `defineExplainer` and `precompute` (in `./core`): a definition is the simulation, the default input (with optional `serialize` / `parse` for links) and an optional `predict` block. `precompute(def, input?)` runs it to a JSON trace and throws a labelled error for a non-JSON input or step (cycles report kind `cycle`), a simulation that throws, or one that hits `maxSteps`. `resolveInput`, `normalizeOptions` and `assertJsonInput` expose the kit's rules.
- **New (experimental)**: `@sphynxoid/stepwise/kit`: `createExplainer({ definition, view })` / `Explainer`, `useExplainer`, and flat parts (`Stage`, `Narration`, `StepCode`, `ExplainerBar`, `EndNote`, `Predict`, `PredictToggle`) with a default layout that children replace. Explainers keep their frame and input in the URL under their `id` (`link`, default true), share the keyboard (it goes to the one the reader last clicked or focused; until then none takes it, so Space still scrolls the page; `keys={false}` takes an explainer out of routing), and run predict mode from the definition (autoplay holds at `at`, graded against the next frame, so a checkpoint on a frame with no successor is skipped; `hint` after two misses). `useExplainer()` reports the run's `error` and `truncated` (development builds log a throwing simulation once). `Predict` and `EndNote` wrap their prose in a `div`, so MDX paragraphs nest validly. `autoPlay` defaults to false. Props are typed (`ExplainerInstanceProps`): the default input's fields are optional props typed from the input (`FieldOverrides`), and an unknown prop is a type error. Fields named like the explainer's own props (`EXPLAINER_PROP_NAMES`: `id`, `theme`, ...) are never read from props, on the server or the client; set them through `input`. Without a definition an explainer plays a recorded `trace` and ships no simulation code.
- **New (experimental)**: `@sphynxoid/stepwise/kit/mdx`: `precomputed(definition, Client)`, a hook-free server component that computes the trace where the page renders and passes it as `trace` (its props are the client component's minus `trace`), and `stepwiseComponents`, the parts plus `Term` / `GlossaryAppendix` as one map for `mdx-components.tsx`. The first frame is server-rendered with or without it; it turns a broken definition into a build error, and in an RSC host (the Next.js App Router) it saves the simulation re-run on hydration. In a non-RSC SSR host (Docusaurus, the Next.js Pages Router, Remix) the wrapper runs again in the browser, so the simulation runs once there too.
- **New**: `useSimulation({ initialTrace })`: while the input (by content) and the seed match a precomputed trace, the hook plays it without running the simulation (the match ignores the simulation's identity and `maxSteps`); an input change recomputes as usual. The `PrecomputedTrace` type is exported from the root entry too.
- **Fix**: a malformed linked input (`#in=%`, not valid percent-encoding) falls back to the default input instead of throwing on mount.
- **Fix**: `useTrace` with a timeline derived in render (`BUILDS.slice(0, n)`, a new array with the same steps every render) no longer loops ("Maximum update depth exceeded", React #185) or undoes player moves (a timer tick, `goLive`, a seek). An array with the same length and, at every index, the same step object or key is not a new trace; and re-anchoring forces its extra commit only when it moved the cursor.
- **Fix**: a link pasted into a tab already on the page (a `hashchange`) restores its input (`syncInput`) and choices (`syncChoices`), then its frame. The frame used to be applied to the old input's trace.
- **Fix**: `TourCard` and `TourSpotlight` portal to `<body>` after mount (like the glossary tooltip). Rendered inside a filtered or transformed ancestor, such as a sticky header with `backdrop-blur`, `position: fixed` resolved against that ancestor and the card landed above the viewport. `TourSpotlight` also looks its target up again when the tracked node is detached (a re-keyed subtree, an HTMX or Turbo swap) instead of tracking a node at 0,0.
- **New (experimental)**: predict's `at(step, frame, next)` gets the frame the guess is graded against, so a checkpoint can depend on what comes next without a lookahead field in every step. Non-breaking.
- **New (experimental)**: `defineExplainer` without `input`, for an explainer with nothing to edit (a recorded walkthrough): the input is `null` and there are no field props. A simulation that reads an input still has to declare one (a type error otherwise). An input typed with an index signature (`Record<string, ...>`) gets no field props either.
- **New (experimental)**: `fromGraph` types its node ids: called without type arguments, it infers the symbols from the edges and the ids from the keys of `nodes`, and checks `start`, the edges, `accept` and `otherwise` against them, so `delta`, `.graph` and the steps carry the id union and an unknown node is a type error. `fromGraph<Sym>(...)` keeps working, with ids as `string`.
- **New (experimental)**: walk explainers. `defineExplainer({ walk, choose: { options } })` takes a `WalkSimulation` instead of a `simulation` (never both; a type error, and a throw from plain JS): the run stops at every `await: true` step until the reader picks an option. The choice type is inferred from the walk and options outside it are a type error. The kit links the choices as `#<id>.path=` (restored before the frame, same-tab links too; `choose.parse`, by default membership in the options, rejects a bad link), exposes them as `useExplainer().walk`, and the new `Choices` part (in the default layout; nothing for a simulation) renders them. `precompute(def, input?, choices?)` replays a walk and returns its `choices`; `precomputed` works unchanged. No `predict` on a walk.
- **New (experimental)**: `StepParts` / `useStepParts`: `Narration`, `StepCode`, `ExplainerBar` and `EndNote` outside an explainer, around any `useTrace` / `useSimulation` / `useWalk` result (`<StepParts source={trace}>`). The explainer opens one for its own parts, so a custom part that reads `useStepParts()` works in both.
- **New (experimental)**: `useWalk({ initialTrace })`, like `useSimulation`'s: a precomputed path plays without running the walk while the input, the seed and the choices match.
- **New**: `PlayerBar controls="step"`: ← scrubber →, no Play button, for timelines the reader steps through (a walk that stops at every choice). `ExplainerBar` takes it too and defaults to it for a walk explainer, whose keyboard leaves Space to the page. The default stays `"full"`.
- **Changed**: `alignTracks` moved to its own pure module (`align-tracks.ts`) so `./core` can carry it. Still exported from the root, unchanged.
- **Build**: a `typecheck` script (`tsc --noEmit`, which also checks the type-level prop tests) runs in `prepublishOnly` and CI. Two tsup configs share `dist/`. The pure code exists once, in the banner-free `core` bundle (a chunk shared with `kit/mdx`); the client bundles import `./core.js` at runtime through an esbuild resolve rule instead of carrying a copy. Client `.d.ts` files inline their own copies of the pure types, which match `core.d.ts` structurally. `clean` now runs as a script before tsup.
- **Correction**: earlier notes (0.3.0) and docs called `runSimulation` from the root entry "server safe". The root entry is a client module, so a React Server Component that imports from it gets a client reference, not a function. On a server or in a build script, import pure functions from `@sphynxoid/stepwise/core`.
- **Demo**: `/qa` drops its workarounds: no lookahead field for predict, no placeholder inputs, no casts on graph ids, no memoized slice for the CI feed, and the tour renders next to its button inside the blurred nav. §05 (be the tester) is a walk explainer now: precomputed, with the kit's narration, "why" box, bar and keys, and `Choices` in its frame. Both walks (`/qa` §05, `/automaton`'s "be the automaton") use the step-only bar.
- **Demo**: `/kit`: two binary-search explainers from one definition and one view, precomputed on the server, with separate links and keyboard focus, one in a custom layout with predict mode.
- **Docs**: LLMS.md section 9; the Next.js + MDX recipe rebuilt around the kit (`stepwiseComponents` in `mdx-components.tsx`); "The core/client boundary" and "The authoring kit" in docs/ARCHITECTURE.md; the API reference's "Experimental: authoring kit" group.

## 0.5.0 — 2026-11-02

Transitions: a trace becomes a graph. Everything new is in the new
`@sphynxoid/stepwise/experimental` entry point and may change in a minor
release; the root entry is unchanged.

- **New (experimental)**: `useWalk` / `runWalk`: simulations that branch on the reader's choices. A step with `await: true` is a choice point, and that `yield` returns the choice. `choose()` answers the choice point under the playhead: at the end the walk continues; a different answer on an earlier one cuts off the old future. A walk is (simulation, input, seed, choices); `syncChoices` puts the choices in the URL so a link replays the path. `anchor: "index"` keeps the position on input edits for walks where step i means "after i inputs".
- **New (experimental)**: `fromGraph`: a declared automaton (nodes, labeled edges, accept states, an `otherwise` dead state), run over a word and drawable from `.graph`.
- **New (experimental)**: `diffTraces` / `structuralEqual`: which steps an edit changed (`useWalk` exposes `lastChange`).
- **Fix**: a checkpoint (`holdAt`) on the last frame now holds; playback used to end there instead.
- **Demo**: `/automaton`: a divisible-by-3 automaton run and drawn from one declaration, and a "be the automaton" walk where wrong answers take a detour.
- **Docs**: "The model" in docs/ARCHITECTURE.md; LLMS.md section 8.

## 0.3.0 — 2026-11-01

Live traces and evaluators. Additive; no breaking changes.

- **New**: `useSimulation(simulation, input, opts)` — a live trace. A simulation is a generator `(input, { rng }) => Iterable<step>`; change the input (or `seed`) and the trace is recomputed while the playhead stays on the same logical step and playback continues. Returns every `useTrace` field plus `steps`, `truncated`, `error`, `seed`. Pure pieces: `runSimulation` (module scope / server safe, `maxSteps` cap, keeps partial steps on a throw) and `createRng(seed)` (seeded mulberry32; string seeds hashed), the only randomness a simulation should use so runs replay exactly.
- **New**: `StepwiseStep.key` — stable step identity across re-runs. `useTrace` re-anchors keyed traces when `steps` changes: the playhead goes to the latest step whose key both traces share (`reanchor`, exported pure). Custom identity via `keyOf`. Unkeyed traces keep the old behavior (same index, clamped).
- **New**: player checkpoints — `useStepPlayer({ holdAt })` pauses autoplay on chosen frames and reports `held` until `release()`. Manual steps and seeks are never held; pressing play releases; `start()` re-arms. On `useTrace`/`useSimulation`, `holdAt` also receives the step.
- **New**: following the live edge — `useStepPlayer({ follow: true })` (and `useTrace` / `useSimulation`) for timelines that grow while watched: a stream, a log, an agent's steps, a game's move history. A reader who is live (playing, or parked on the last frame) plays into appended frames at the normal pace; one who scrubbed back stays put. `player.live` and `player.goLive()` drive a "Go live" control, and `PlayerBar live` renders one. Checkpoints still hold; a following `autoPlay` player can mount empty. Appends to a keyed trace skip re-anchoring (same key at the same index).
- **New**: `player.jump(frame)` — move the cursor without touching play state (re-anchoring, restoring linked state).
- **New**: evaluators — `Verdict { status: "pass" | "fail" | "pending", feedback }` and `Evaluator<Ctx> = (ctx, signal) => boolean | Verdict | Promise<…>`, with `pass` / `fail` / `pending` / `toVerdict`. `useEvaluator(evaluator, ctx, { mode })` keeps the verdict as state: `"auto"` re-judges on context change (gates), `"manual"` on `check()` (quizzes) and clears when the answer changes; async checks report pending, abort superseded runs and drop late results; `attempts` for hints.
- **New**: tour gates may return a `Verdict`: anything but pass blocks Next, and `tour.feedback` carries the message; `TourCard` takes `feedback` and announces it politely.
- **New**: `readHashParam` / `writeHashParam` are public, for pages that keep their own state in the fragment next to a player's `syncHash` key.
- **Fix**: on mount, the player's hash writer no longer puts the stale index back into the URL in the same commit that reads a linked frame (sibling effects saw `#frame=0`).
- **Fix**: the player re-read the URL frame on every timeline length change, which could override the playhead after a recompute. It now reads on mount, on `hashchange`, and when the first non-empty timeline arrives.
- **Demo**: `/simulate` — edit an insertion sort's input while it plays (the step stays put, links replay exactly), plus a predict mode built from checkpoints and a manual evaluator. `/live` — a build log streaming in: follow the edge, scrub back to inspect an event, then Go live. `/discovery`'s query gate now explains what's missing.

## 0.2.0 — 2026-11-01

- **New**: `useTrace(steps, opts)` — a player bound to a typed trace. Returns `{ player, step, frame, toneAt, titleAt }`; `step` is frame 0 before playback starts, and the scrubber accessors are stable.
- **New**: `StepwiseStep<Data>` is generic — carry your domain payload in the step type (`StepwiseStep<{ arr: number[] }>`). The default (`StepwiseStep`) is unchanged.
- **New**: `useStepPlayer({ respectReducedMotion })` (default `true`) — with `autoPlay`, users who prefer reduced motion land on frame 0, paused.
- **New**: `createTrace<Data>()` — a typed trace builder (`.step()`, `.length`, `.last()`, `.build()`) so traces are built at module scope without IIFEs. `build()` returns `StepwiseStep<Data>[]` snapshots.
- **New**: `useSyncedTracks(tracks, opts)` — comparison mode: several traces under one player. Shorter tracks hold their last frame, or align steps on shared sync keys (`key`). Returns per-track views (`step`, `index`, `held`, `done`) plus stable `toneAt`/`titleAt`. `alignTracks` exposes the pure alignment.
- **New**: `useLessonStream(count, opts)` — headless windowed notebook reader: mounts a window around the seed lesson, loads neighbours on approach, compensates the scroll for content prepended above the reader, and tracks the active lesson by viewport center. Composes with `ChapterNav` / `LessonPager`. `useFadeIn` fades streamed blocks in.
- **Fix**: `useStepPlayer` and `useGuidedTour` control callbacks are now referentially stable (they were re-created every frame, breaking memoized children and effect deps). `useChapters` and `useGuidedTour` return memoized objects.
- **Fix**: `syncHash` no longer overwrites the whole URL fragment — it updates only its own `key=value` part and keeps anchors and other keys. Keys are matched literally (previously interpolated into a regex unescaped).
- **New**: precompiled stylesheet `@sphynxoid/stepwise/styles.css` — styles the components without Tailwind. Only the kit's own classes, no global preflight (scoped to `[data-stepwise]` roots), no global theme variables; colors are `--stepwise-*` tokens with light/dark defaults (`prefers-color-scheme`, `.dark` / `[data-theme]`). Built by the Tailwind CLI (`npm run build:css`, part of `build`).
- **New**: shadcn registry served by the demo at `/r/*.json` — `npx shadcn@latest add https://stepwise.thesphynx.net/r/player-bar.json` copies the component source (`player-bar`, `code-block`, `tour`, `glossary`, `chapter-nav`, `lesson-pager`, `shortcuts-dialog`, or `stepwise` for all) into your repo; hooks stay imported from the package. Generated from the library source on every demo build.
- **Change**: styled component roots carry a `data-stepwise` attribute (the stylesheet's preflight scope).
- **Docs**: npm README uses the `@sphynxoid` scope and the `dist` `@source` path. TAILWIND-SETUP covers all three styling routes and documents the shadcn token contract (including the `accent` caveat and the dark-host `white/N` overlays).

## 0.1.0 — 2026-10-27

Initial release.

- **Core**: `useSteps` — a clamped cursor over an ordered sequence, with stable callbacks and automatic re-clamping.
- **Policies**: `useStepPlayer` (timer, speed, seek, `#hash` deep links, `PlayerEngine` port; a completion state `ended` and `onEnd` callback — distinct from the `atEnd` position flag — with engine adapters firing `onEnd` once per run on the transition into the final frame), `useGuidedTour` (`onEnter` effects, `TourDriver` port, plus conditional tours: `when` skip predicates, `gate` guards with a `blocked` flag, `next` edge overrides by step id, `gotoId`), `useChapters` (viewport-center scroll tracking), `useDiscoveries` (persisted discovery ledger with `localStorageStore` / `cookieStore` / `memoryStore` storage seams — pair with a tour for show-once feature tutorials).
- **Utilities**: `useGlobalKeys`, `useFocusTrap`, `usePrefersReducedMotion`, `flattenChapters`.
- **Presentation**: `PlayerBar`, `StepScrubber` (with `groupOf` sub-chapter grouping), `ChapterNav`, `LessonPager`, `TourSpotlight`, `TourCard` (with `nextDisabled` for gated steps), `ShortcutsDialog` (focus trap, Escape, portal), `CodeBlock`; `GlossaryProvider` / `Term` / `GlossaryAppendix`; injectable `StepwiseTheme` (surface, overlay, code block, kbd, spotlight, muted tokens).
- **Adapters** (opt-in subpaths): `./adapters/gsap`, `./adapters/driver-js`, `./adapters/scroll`.

### Packaging notes

- The root barrel is dependency-free beyond React — adapters live behind `./adapters/*` subpath exports so optional peers (gsap, driver.js) are never required imports.
- `sideEffects` declares the driver.js adapter's CSS import; everything else tree-shakes.
- The build re-adds the `"use client"` directive as a banner (esbuild strips per-file directives while bundling), so React Server Components can import the package.
